JOURNEY · 07

What happens after Kestrel receives the request?

I finally understood who receives the HTTP request. But Kestrel was only the beginning. I now needed to understand how ASP.NET Core processes that request.

01

THE QUESTION

The Kestrel receives the request. Then What?

I had learned that Kestrel is responsible for the web-server side of communication.

It receives the HTTP request and passes it into the ASP.NET Core application.

But that created another question:

Once ASP.NET Core receives the request, who decides what should happen to it?
02

THE PROBLEM

Every request may need common processing.

Imagine an application with hundreds of controllers.

Many requests may need common operations such as logging, authentication, error handling, or checking whether a request should continue.

We could put these checks inside every controller. But that would create duplicated logic and make the application harder to maintain.

Controller A Logging
Controller B Logging
Controller C Logging

There had to be a better way to handle functionality that applies to many or most requests.

03

THE IDEA

what if requests passed through a common chain?

Instead of putting the same logic into every controller, ASP.NET Core allows us to place common request-processing logic into components called middleware

Each middleware can perform some work and then decide whether the request should continue to the next component.

HTTP Request
↓ Middleware 1 ↓ Middleware 2 ↓ Middleware 3 ↓
Endpoint
04

THE REQUEST PIPELINE

This chain became the request pipeline.

The ASP.NET Core request pipeline is the sequence of middleware components through which an HTTP request passes.

Each middleware can perform work before passing the request forward.

Middleware can also perform work after the next component has finished processing the request.

Request Enters pipeline
↓
Middleware Process
↓
Next middleware Continue
↓
Endpoint Handle request
05

WHY MIDDLEWARE?

Common behavior can live in one place.

This was the architectural idea that finally made middleware useful to me.

If many requests need the same functionality, that functionality can be placed into middleware instead of being repeatedly implemented in controllers.

Logging

Record information about incoming requests and outgoing responses.

Authentication

Establish the identity assocated with the request.

Error handling

Handle failures consistently instead of repeating the same logic everywhere.

Authorization

Apply access-control decisions before protected functionality executes.

06

ORDER MATTERS

Middleware is not just a collection of components.

Another important realization was that middleware executes in a specific order.

The order matters because one middleware can affect what the next middleware receives or whether the request reaches it at all.

Middleware A ↓ Middleware B ↓ Middleware C 2 ↓ Endpoint

So when I look at middleware configuration in Program.cs, the order of those registrations is part of the application's behaviour.

07

PROGRAM.CS AGAIN

Program.cs was starting to make sense.

I had previously seen code such as: 

                            
                                app.UseAuthentication();
                                app.UseAuthorization();
                                app.MapControllers();

I could now see that these lines were not random configuration statements.

They were helping define how requests should be processed by the application.

Program.cs Configure application ↓
Middleware Process request
↓
Endpoint Execute application code
08

ARCHITECTURE VIEW

The pipeline separates common request concerns from application logic.

This was the point where I started looking at ASP.NET Core from a more architectural perspective.

Controllers should primarily deal with application behaviour rather than repeatedly implementing cross-cutting concerns such as logging, authentication, or centralized error handling.

Middleware gives the application a place to handle those concerns around the request-processing flow.

Request
↓
Cross-cutting concerns Middleware
↓
Application logic Controllers / endpoints
↓
Response

THE BIGGER PICTURE

The entire request journey was becoming visible.

I could now connect the pieces i had learned so far.

10

INTERVIEW DEPTH

Can I explain the request pipeline properly?

What is the ASP.NET Core request pipeline?

It is the sequence of middleware components through which an HTTP request passes before reaching the appropriate endpoint, with the response travelling back through the pipeline.

Why do we need middleware?

Middleware provides a centralized wasy to implement request-processing behaviour that may apply accross multiple endpoints, such as logging, authentication, authorization, exception handling, and other cross-cutting concerns.

Does every middleware have to pass the request forward?

No. Middleware can choose not to call the next component. In that case, the pipeline can terminate at that middleware instead of continuing toward the endpoint.

Why does middleware order matter?

Middleware executes in the order it is added to the pipeline for the incoming request. Therefore, changing the order can change application behaviour.

Is middleware the same as a controller?

No. Middleware participates in the request pipeline and can operate on many or all requests. A controller action is application-level endpoin logic selected after routing determines the appropriate endpoint.

What is the architectural benefit?

Middleware allows common request concerns to be separated from individual endpoint implementations, reducing duplicaiton and keeping application logic focused on its actual responsibility.
