JOURNEY · 08

How does ASP.NET Core know which action should handle a request?

I understood that Kestrel receives the HTTP request and that the ASP.NET Core request pipeline processes it. But something was still missing: when the request reaches the application, how does it know where the request should go?

01

THE QUESTION

A request has arrived. But who decides where it goes?

By this point in my journey, I had a better picture of what happens before the application handles a request.

The browser sends an HTTP request. Kestrel receives it and passes it into the ASP.NET Core request-processing pipeline.

Browser Sends HTTP request
↓
Kestrel Receives request
↓
ASP.NET Core Request pipeline

But now I had another question.

If my application has many controllers and many action, how does ASP.NET Core know which one should handle this request?
02

THE PROBLEM

An application can have many possible destinations.

Imagine an application with these actions: 

                            
                                [HttpGet("products")]
                                public IActionResult GetProducts()
                                {
                                    ...
                                }

                                [HttpGet("products/{id}")]
                                public IActionResult GetProduct(int id)
                                {
                                    ...
                                }

                                [HttpPost("products")]
                                public IActionResult CreateProduct(Product product)
                                {
                                    ...
                                }

Now suppose the application receives: 

                            
                                GET /products/25/

The application needs some mechanism to determine which action is the intended destination.

I initially thought about this as simply "finding the controller."

But that mental model turned out to be incomplete.

03

THE .NET ANSWER

This is where routing comes in.

Routing is responsible for determining which endpoint should handle an incomning request.

The key question routing answers is:

Which endpoint should handle this request?

This immediately changed how I thought about routing.

Routing is not simply "sending a request to controller." Its job is to examine the request and the application's available endpoints and select the appropriate endpoint.

04

FIRST IMPORTANT DISTINCTION

Routing selects an endpoint. It doesn't redirect the request.

I initially used the word "redirect" when thinking about routing.

But that can create the wrong mental model.

In HTTP, a redirect normally means that the server tells the client to make another request, usually using a 3xx status code.

Routing is different.

HTTP Request GET /products/25
↓
Routing Selects endpoint
↓
Endpoint GetProduct()

So the better sentence is:

Routing selects the matching endpoint that should handle the request.
05

WHAT IS AN ENDPOINT?

An endpoint is more than just a URL.

This was another important part of the investigation.

I initially thought of an endpoint as simply a URL. But an endpoint represents a destination that the application can execute.

Route /products/{id}
+
HTTP Method GET
+
Handler GetProduct()

the diagram above is a simplefied model rather than a literal definition of how an Endpoint object is constructed.

Conceptually, I can think of an endpoint as something containing information such as:

  • the route pattern
  • the HTTP method
  • the handler (code) that can execute when the endpoint is selected
  • metadata assocated with that endpoint

For example; 

                            
                                Route: /products/{id}
                                Method: GET
                                Handler: ProductController.GetProduct()

This gives me a better mental model of what routing is actually selecting.

Routing does not simply select a URL. It selects an endpoint that represents an executable destination for the request.
06

WHERE DO ENDPOINTS COME FROM?

The controller action provides routing information.

Consider: 

                            
                                [HttpGet("products/{id}")]
                                public IActionResult GetProduct(int id){
                                    ...
                                }

The attribute tells ASP.NET Core important information about how this action can be reached.

The route pattern is: 

                            
                                /products/{id}

And the action accepts the HTTP GET method.

So the framework has information associated with this action that can eventually be respresent as part of an endpoint such as: 

                            
                                GET /products/{id}
                                 ↓
                                ProductController.GetProduct()

This does not mean that the controller action itself is the endpoint. Rather,the action contributes information that is used when the application's endpoint information is built.

A controller action provides routing information that can become part of an executable endpoint.
07

APPLICATION STARTUP

Where does MapControllers() fit into this?

This connected routing back to something I had already learned in Program.cs. 

                            
                                var builder = WebApplication.CreateBuilder(args);
                                builder.Services.AddControllers();
                                var app = builder.Build();
                                app.MapControllers();
                                app.Run();

I had to be careful not to think that MapControllers() itself contains all the route definition.

The controller actions provide routing metadata through their attributes. ASP.NET Core can discover that information and use MapControllers() to map the controller actions into the application's endpoint system.

Controller Action Route attributes
↓
Endpoint Mapping MapControllers()
↓ Endpoint Information

At this point, the application has the endpoint information that routing can use when request arrive.

But routing has not yet selected an endpoint for a specific request. That happens at request time.

The important distinction is:

During application startup, controller actions are mapped into the endpoint system. At request-time, routing uses that endpoint information to select an endpoint.
08

REQUEST TIME

Routing uses endpoint information when a request arrives.

Once the application is running, a request might arrive: 

                            
                                GET /products/25

Routing now needs to determine which available endpoint matches this request.

GET /products/25
↓ Routing ↓
GET /products/{id}
↓
ProductController.GetProduct() Endpoint handler

At this point, I can see the difference between what happens when the application starts and what happens when an actual request arrives.

  • Startup: controller actions are discovered and mapped into the endpoint system.
  • Request time: routing examines the incoming request against the available endpoint information and determines the appropriate endpoint.

But this raises another question.

What happens when more than one endpoint appears to match the request?
09

CANDIDATE ENDPOINTS

Routing doesn't immediately jump to one action.

This was another part of my mental model that needed correction.

It is better to think of routing as examining the available endpoints for the incoming request.

The routing process then uses things such as the route pattern, constraints, and HTTP method requirements to determine which candidate is valid and should be selected.

Incoming Request
↓
Candidate Endpoints Possible matches
↓
Routing Rules Route / Constraints / HTTP Method
↓ Selected Endpoint

So I should not imagine routing as: 

                            
                                "Find something that looks close enough and use it."

Instead, I should think of it as: 

                            
                                "Examine the possible candidates and select the endpoint that validly matches the request."

This also explains why routing needs more information than just the URL path.

For example, these two endpoints could have the same route path but accept different HTTP methods: 

                            
                                [HttpGet("products")]
                                GetProducts()

                                [HttpPost("products")]
                                CreateProduct()

The request's HTTP method therefore matters when determining which endpoint can handle the request.

Routing examines possible endpoint candidates and uses the request and endpoint metadata to determine which endpoint should be selected
10

HTTP METHOD

The path alone isn't enough.

Consider: 

                            
                                [HttpGet("products")]
                                public IActionResult GetProducts(){
                                    ...
                                }

                                [HttpPost("products")]
                                public IActionResult CreateProduct(Product product){
                                    ...
                                }

Both actions use the same path: 

                            
                                /products

But they accept different HTTP methods.

GET /products GetProducts()
vs
POST /products CreateProduct()

Therefore, the HTTP method is one of the important pieces of information routing uses when determining which endpoint can handle a request.

The same path can therefore lead to different endpoints depending on the HTTP method.

GET /products
↓
GetProducts()
  vs  
POST /products
↓
CreateProduct()

So I should not think of a request as only: 

                            
                                /products

I should think of it as including at least: 

 
                             
                                HTTP Method + Path 

                                GET + /products 
                                POST + /products
The path alone isn't enough. The HTTP method also matters when determining which endpoint can handle the request.
11

LITERAL VS PARAMETER ROUTES

What happens when two routes appear to match?

Consider: 

                            
                                [HttpGet("products/all")]
                                public IActionResult GetAll(){
                                    ...
                                }

                                [HttpGet("products/{id}")]
                                public IActionResult GetProduct(int id){
                                    ...
                                }

Now the request is: 

                            
                                GET /products/all

At first glance, both routes seem capable of matching: 

                            
                                /products/all 
                                /products/{id}

The reason the second route can appear to match is that {id} is a route parameter, so without any constraint it can match the value all as well.

But they are not equally specific.

The first route contains a literal segment: 

                            
                                products/all

The second route contains a parameter segment: 

                            
                                products/{id}

The literal route has higher route precedence than the parameter route for this request.

/products/all Literal
>
/products/{id} Parameter

Therefore: 

                            
                                Get /products/all
                                    ↓
                                GetAll()

This is an example of route precedence: when multiple route patterns can match, the more specific route can take precedence over a more general route.

This corrected another terminology mistake in my thinking: I should say literal route, not "linear route."

A literal route is more specific than a paramater route, so it can take precedence when both pattersn match the request.
12

ROUTE CONSTRAINTS

A route parameter can have constraints.

Consider: 

                            
                                [HttpGet("products/{id:int}")]
                                public IActionResult GetProduct(int id){
                                    ...
                                }

The :int part is a route constraint. It says that the route value for id must satisfy the integer contraint for this route to be considered a match.

Therefore: 

                            
                                GET /products/25

satisfies the contraint.

But: 

                            
                                GET /products/abc

does not satisfy the integer contraint.

/products/25 int constraint passes
→
GET endpoint Candidate remains valid
/products/abc int constraint fails
→
GET endpoint Not a matching candidate

An important detail is that the :int constraint is part of routing. It helps determine whether this route can match the incoming request.

It should not be confused with model binding. The constraint does not mean that routing has already converted the route value into a C# int.

A route constraint restricts which values can match a route. It helps routing determine whether an endpoint is a valid candidate.
13

CONSTRAINTS VS MODEL BINDING

This is where routing and model binding must be separated.

Consider: 

                            
                                [HttpGet("products/{id}")]
                                public IActionResult GetProduct(int id){
                                    ...
                                }

And: 

                            
                                GET /products/abc

The route pattern can match this path because {id} does not have an integer constraint.

Routing can therefore select the endpoint and produce a route value conceptually like: 

                            
                                id = "abc"

But the action requires: 

                            
                                int id

Model binding now has the responsibility of preparing the action parameter. It attempts to provide the incoming value to the type expected by the action. 

                            
                                "abc" → int

The conversion cannot succeed because "abc" is not a valid integer value.

Now compare this with: 

                            
                                [HttpGet("products/{id:int}")]
                                public IActionResult GetProduct(int id){
                                    ...
                                }

In this case, the request: 

                            
                                GET /products/abc

fails the int route constraint during routing. Therefore this endpoint is not considered a valid match for the request.

/products/{id} No int constraint
↓
Routing Endpoint can match
↓
Model Binding "abc" → int
/products/{id:int} int constraint
↓
Routing Constraint fails
↓ Endpoint not selected
A route constraint can eliminate an endpoint during routing. Model binding can fail later while preparing the action parameter.
14

ANOTHER EXAMPLE

A general route can compete with a contrained route.

Suppose we have: 

                            
                                [HttpGet("products/{id:int}")]
                                public IActionResult GetById(int id){
                                    ...
                                }

                                [HttpGet("products/{name}")]
                                public IActionResult GetByName(string name){
                                    ...
                                }

Now consider this request: 

                            
                                GET /products/25

Both route patterns can initially appear capable of matching this path. 

                            
                                /products/{id: int}
                                /products/{name}

But the first endpoint has an integer contraint, and 25 satisfies that constraint.

The constrained therefore narrows the values that can match that endpoint.

/products/25
↓
Candidate Endpoints
↓
/products/{id:int} Constraint passes

Now change the request: 

                            
                                GET /products/abc

The :int constraint fails because abc is not an integer.

That endpoint is therefore eliminated as a matching candidate.

The general route does not have an integer constraint, so it can still match: 

                            
                                /products/{name}
                                        ↓
                                    name = "abc"
/products/abc
↓
/products/{id:int} Constraint fails
×
/products/{name} Valid candidate

So the result depends on the value in the incoming request. The constrained route can match integer values, while the general paramater route can match values that do not satisfy the integer constraint.

A route constraint narrows which values can match an endpoint. If the constraint fails, that endpoint is removed from consideration for that request.
15

AMBIGUITY

What happens when multiple endpoints remain equally valid?

Consider: 

                            
                                [HttpGet("products/{id}")]
                                public IActionResult GetById(string id){
                                    ...
                                }

                                [HttpGet("products/{code}")]
                                public IActionResult GetByCode(string code){
                                    ...
                                }

Now: 

                            
                                GET /products/25

Both routes have the same structure: 

                            
                                /products/{id}
                                /products/{code}

The parameter names do not make one route more specific than the other.

Both endpoints can therefore remain valid candidates for the same request.

Endpoint A /products/{id}
+
Endpoint B /products/{code}
→ Ambiguous match

ASP.NET Core should not randomly choose between these endpoints because the routing information does not provide a clear way to determine which one was intended.

Instead, the framework treats this as an ambiguous match rather than silently selecting one of the actions.

This is different from the earlier examples. 

 
                             
                                /products/all 
                                    ↓ 
                                /products/all 
                                    ↓ 
                                More specific route

In that example, route precedence provided a distinction. Here, both route patterns have the same structure, so the parameter names alone do not provide that distinction.

This taught me another useful architectural principle:

When the framework cannot determine the intended destination, it should not silently guess.
16

ROUTE PARAMETERS

What exactly happens to the value in the URL?

Until this point, I understood that routing can match a request and select an endpoint. But another question appeared:

What actually happens to the value 25 in /products/25

Consider: 

                            
                                [HttpGet("products/{id}")]
                                public IActionResult GetProduct(int id){
                                    ...
                                }

And the incoming request: 

                            
                                GET /products/25

The {id} in the route template is a route parameter, or placeholder. 

                            
                                /products/{id}
                                          ↑
                                        placeholder

When the actual request arrives: 

                            
                                /products/25

The route parameter matches the corresponding value in the URL.

/products/25
↓
/products/{id}
↓
Route value id = "25"

Conceptually, routing can provide a route value like: 

                            
                                id = "25"

That is an important distinction.

The route value is not automatically the same thing as the C# action parameter: 

                            
                                Route value

                                id = "25"

                                C# action parameter 

                                int id

At this point, routing has done its job of matching the request and selecting the endpoint. The next question is how the route value eventually becomes the value required by the action parameter.

Routing can provide route values from the matched URL. Preparing those values for the action parameter is a separate responsibility.
17

ROUTING VS MODEL BINDING

Routing does not directly create the C# action parameter.

This was probably the most important correction in my mental model.

GET /products/25
↓ Routing ↓
Route value id = "25"
↓ Model Binding ↓
int id = 25

Routing's responsibility is to match the request against endpoint information and select an endpoint. It can also produce route values from the matched route.

Model binding then uses request data, including route values, to prepare the parameters required by the selected action.

So the value in the URL and the C# parameter are related, but they are not the same thing. 

                            
                                URL value
                                    ↓
                                   "25"
                                    ↓
                                Model Binding
                                    ↓
                                int id = 25

This distinction becomes even more useful when the action receives values from different parts of the request, such as route values, query string values, or the request body.

Routing selects the destination. Model binding prepares the inputs.
18

QUERY STRING

Not all action parameters come from the route.

This raised another question:

What happens when some data comes from the route and some data comes from somewhere else in the request?

Consider: 

                            
                                [HttpGet("products/{id}")]
                                public IActionResult GetProduct(int id, string sortBy){
                                    ...
                                }

Request: 

                            
                                GET /products/25?sortby=price

There are now two different pieces of request data.

/products/25 Route
+
?sortBy=price Query string

The route value and query string value come from different parts of the request. 

                            
                                Route value:
                                id = "25"

                                Query string:
                                sortBy = "price"

The query string is not part of the route template /products/{id}. It is additional request data that can also be used by model binding. 

                            
                                int id = 25
                                string sortBy = "price"
Route id = "25"
+
Query String sortBy = "price"
↓ Model Binding ↓
Action Parameters id = 25, sortBy = "price"
Route values and query string values are different sources of request data, and model binding can use both to prepare action parameters.
19

EXPLICIT SOURCES

We can explicitly tell model binding where a value come from.

ASP.NET Core provides attributes such as: 

                            
                                [FromRoute]
                                [FromQuery]
                                [FromBody]

For example: 

                            
                                [HttpGet("products/{id}")]
                                public IActionResult GetProduct([FromRoute] int id, [FromQuery] string sortBy){
                                    ...
                                }

This makes the intended sources explicit: 

                            
                                id → route
                                sortBy → query string

We can also explicitly tell model binding to get a value from the request body: 

                            
                                [FromBody] Product product

So these attributes can make the source of an action parameter explicit:

[FromRoute] Route values
+
[FromQuery] Query string
+
[FromBody] Request body
↓ Model Binding

An important detail is that these attributes are primarily about model binding, not about telling routing which endpoint to select.

Routing still uses information such as the route pattern and HTTP method to determine which endpoint can handle the request.

Routing selects the endpoint. Model binding determines where the action's input values come from and prepares them for the action parameters.
20

COMPLEX OBJECTS

Routing can select the action , but the action may need much more data.

Consider a POST request: 

                            
                                [HttpPost("products")]
                                public IActionResult CreateProduct(Product product){
                                    ...
                                }

The request might contain: 

                            
                                POST /products

                                Content-Type: application/json 
                                {
                                    "name": "Laptop",
                                    "price": 500000
                                }

There is no product information in the route.

The route only tells ASP.NET Core that this is a POST /products request.

Routing's job is to determine which endpoint can handle this request.

The request body is a separate concern.

POST /products Request
↓ Routing ↓
CreateProduct() Selected endpoint
↓ Model Binding ↓
Product Request body data

The request body contains JSON, but the action expects a C# Product object.

For a JSON request body, ASP.NET Core uses an appropriate input formatter to deserialize the JSON into the expected complext type. 

                            
                                JSON 
                                  ↓ 
                                Input Formatter 
                                  ↓ 
                                Product object 
                                  ↓ 
                                CreateProduct(Product product)

So the routing process does not need to understand the product's properties such as name or price

Routing selects the endpoint. Model binding, together with the appropriate input formatter for a JSON body, prepares the data required by the action.

Routing selects the destination. The request body is handled separately and can be deserialized into a complex object for the selected action.

                                [HttpPut("products/{id}")]

                                ↓

                                id = 15

VALIDATION

Successfully binding a value does not mean the value is valid.

This distinction became clear when looking at a product price. 

                            
                                {
                                    "name": "Laptop",
                                    "price": -50000
                                }

If the JSON can be Successfully deserialized into a Product, binding may succeed.

The value -50000 is still a valid numberic value, so there may be no problem converting it into the expected C# type.

But the application can still decide that a negative price is invalid.

JSON Incoming data
↓
Binding Can I provide the action parameter?
↓
Validation Is the resulting data acceptable?

This gave me another useful distinction. 

 
                             
                                "price": -50000 
                                    ↓ 
                                Binding 
                                    ↓ 
                                Product.Price = -50000 
                                    ↓ 
                                Validation 
                                    ↓
                                Invalid: price cannot be negative

The important point is that binding and validation answer different questions.

Binding asks whether incoming data can be provided in the required form. Validation asks whether the resulting data is acceptable.
23

THE COMPLETE REQUEST FLOW

Routing finally made sense when I connected it to everything before and after it.

A request such as : 

                            
                                PUT /products/25

                                Content-Type : application/json

                                {
                                    "name": "Laptop", 
                                    "price": 50000
                                }

travels through several different responsibilities.

Browser Sends request
↓ Kestrel ↓ ASP.NET Core Request Pipeline ↓ Routing Selects an endpoint ↓
Selected Endpoint PUT /products/{id}
↓ Model Binding Prepares action inputs ↓ Validation Checks whether data is acceptable ↓
Controller Action Application behavior

Each part of this flow has a different responsibility.

  • Kestrel receives the HTTP request.
  • Middleware in the ASP.NET Core request pipeline can process the request as it moves through the application.
  • Routing examines the request and the available endpoint information to determine which endpoint can handle it.
  • Model binding prepares the values needed by the selected action from request data such as route values, query string values, and the request body.
  • Validation checks whether the resulting data satisfies the application's validation rules.
  • The controller action executes the application behavior.

For this particular request, the route values from: 

                            
                                /products/25
                                    ↓
                                id = "25"

The JSON body provides the product data: 

                            
                                {
                                    "name": "Laptop",
                                    "price": 50000
                                }

Model binding can then prepare the inputs required by the selected action. 

                            
                                id      → 25
                                product → Product object

Only after these responsibilities have been handled does the controller action receive the data it needs to perform its application behavior.

A request is not handled by one single component. Different parts of ASP.NET Core are responsible for receiving the request, processing it, selecting the endpoint, preparing its inputs, validating the data, and finally executing the application behavior.
24

RESPONSIBILITY BOUNDARIES

Each part has a different responsibility.

Kestrel

Handles the web-server side of communication: accepting network connections, receiving HTTP requests, and sending HTTP responses.

Middleware

Processes requests and responses through the ASP.NET Core request pipeline and handles cross-cutting concerns.

Routing

Examines the incoming request and available endpoint information to select an endpoint.

Model Binding

Prepares action parameters from request data such as route values, query strings and request bodies.

Validation

Determines whether the bound data satisfies the application's validation rules.

Controller Action

Executes application behavior after the required endpoint and inputs have been determined.

INTERVIEW DEPTH

Can I explain routing without memorizing a definition?

If I were asked about routing in an interview, I should be able to reason through the request rather than simply recite a definition.

What is routing?

Routing is the mechanism that matches an incoming HTTP request against the application's endpoint information and selects the endpoint that should handle the request.

Does routing select a controller?

More precisely, routing selects an endpoint. In a controller-based application, that endpoint can ultimately invoke a controller action.

What is an endpoint?

An endpoint represents an executable destination in the application, along with information such as its route pattern, HTTP method and metadata.

What happens if two routes match?

ASP.NET Core evaluates the available candidates using things such as HTTP method, contraints, and route precedence. If one valid candidate can be distinguished from the others, it can be selected. If equally valid candidates remain ambiguous, the framework does not simply guess.

What is a route constraint?

A route constraint restricts whether a route parameter value can make an endpoint a valid candidate during routing.

What is the difference between routing and model binding?

Routing determines the endpoint and can produce route values. Model binding then uses request date to prepare the parameters required by that endpoint's action.

Does routing convert "25" into int 25?

Not as its primarily responsibility. Routing produces route information and values. Model binding is responsible for preparing the action parameter and performing the necessary conversion.

What happens when a route contraint fails?

That endpoint is not considered a valid candidate for that request.

What happens when model binding fails?

The endpoint may already have been selected, but the framework cannot successfully provide the expected action parameter from the incoming request data.
